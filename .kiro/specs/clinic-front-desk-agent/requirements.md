# Requirements Document

## Introduction

The Clinic Front-Desk Voice Agent is an administrative automation system for a solo-doctor ENT (ear, nose, throat) clinic. The system pairs a reactive, patient-facing voice front desk with an autonomous, doctor-facing practice-intelligence layer.

The Voice Front Desk answers patient calls and handles appointment booking, rescheduling, cancellation, frequently asked questions, waitlisting, and escalation to a human. It is powered by the Strands Agents SDK as the reasoning and tool-orchestration core and Amazon Nova Sonic (via Amazon Bedrock) as the real-time speech-to-speech voice layer, intended for deployment on Amazon Bedrock AgentCore.

The Practice Intelligence layer runs in the background over accumulated call and booking data, detects operational patterns (no-show trends, schedule gaps, unmet demand), and surfaces concrete decisions to the doctor through a role-aware dashboard.

The system is strictly administrative. It performs no clinical advice, symptom triage, or diagnosis. Patient routing is based only on the department, specialty, or service a patient names, never on interpretation of symptoms. A human makes all clinical and policy decisions, and an escalation path exists for any request outside the agent's administrative rules.

The demo and initial build target a single ENT provider, but the data model is provider-aware so it can extend to multiple providers or departments later. The system starts empty; the doctor onboards clinic configuration, and live bookings populate the data over time.

## Glossary

- **Voice_Front_Desk**: The reactive, patient-facing agent that handles inbound voice calls, orchestrated by the Strands Agents SDK and voiced by Amazon Nova Sonic.
- **Practice_Intelligence**: The autonomous, doctor-facing background agent that analyzes accumulated data and generates decision recommendations.
- **Dashboard**: The role-aware web interface used by the doctor (and optionally one assistant) to review decisions, schedule, call activity, and metrics.
- **System**: The overall Clinic Front-Desk Voice Agent, including the Voice_Front_Desk, Practice_Intelligence, Dashboard, and data layer.
- **Provider**: A clinician who owns a schedule. The demo has one Provider (the solo ENT doctor).
- **Doctor**: The solo ENT Provider who onboards the clinic and uses the Dashboard.
- **Patient**: A person who calls the clinic and interacts with the Voice_Front_Desk by voice only.
- **Appointment**: A scheduled visit associated with a Provider, a Patient, a service, a date, and a time slot.
- **Slot**: A discrete bookable time interval on a Provider's calendar.
- **Waitlist**: An ordered list of Patients requesting a service or slot type that is currently full.
- **Escalation**: The act of routing a request to a human when it falls outside the agent's administrative rules.
- **Decision**: A recommendation generated by Practice_Intelligence that the Doctor can approve or dismiss.
- **Clinic_Knowledge_Base**: The store of onboarded clinic information (hours, location, services, prep instructions, insurance, pricing) used to answer FAQs.
- **AppointmentStore**: The data-access interface for reading and writing Appointment records.
- **PatientStore**: The data-access interface for reading and writing Patient records.
- **Data_Layer**: The collection of data-access interfaces (AppointmentStore, PatientStore, and others) backed by DynamoDB and designed to be swappable.
- **Strands_Tool**: A discrete callable capability exposed to the agent (for example check_availability or book_appointment) that the agent chains in multi-step reasoning.
- **Barge_In**: A Patient speaking while the Voice_Front_Desk is talking, requiring the agent to stop and listen.
- **Call_Session**: A single continuous voice interaction between a Patient and the Voice_Front_Desk.
- **Patient_History**: The record of a Patient's prior Appointments and interactions used across Call_Sessions.

## Requirements

### Requirement 1: Clinic Onboarding and Configuration

**User Story:** As the Doctor, I want to onboard my clinic information before taking calls, so that the Voice_Front_Desk has accurate data to book appointments and answer questions.

#### Acceptance Criteria

1. WHEN the Doctor first accesses the Dashboard AND no clinic configuration exists, THE System SHALL present a clinic onboarding workflow.
2. THE System SHALL allow the Doctor to configure clinic hours as an opening time and closing time for each day of the week, clinic location, offered services (1 to 100 services), preparation instructions (up to 2,000 characters per service), accepted insurance, and a price per offered service in the range 0.01 to 999,999.99.
3. THE System SHALL allow the Doctor to configure between 1 and 50 Providers, each with a name (1 to 100 characters), a specialty, and a bookable schedule expressed as available days and start/end time ranges.
4. WHEN the Doctor saves clinic configuration AND all required fields are present, THE System SHALL persist the configuration to the Clinic_Knowledge_Base through the Data_Layer and indicate save success to the Doctor.
5. IF the Doctor attempts to save clinic configuration with any missing required field, THEN THE System SHALL reject the save, identify each missing required field, and retain the values already entered, WHERE required fields are clinic hours, clinic location, at least one offered service, and at least one Provider.
6. IF persistence of clinic configuration to the Clinic_Knowledge_Base through the Data_Layer fails, THEN THE System SHALL reject the save, indicate to the Doctor that the save failed, and retain the entered values without applying a partial update.
7. WHILE no clinic hours and no offered services are configured, THE Voice_Front_Desk SHALL respond to booking and FAQ requests by informing the Patient that the clinic is not yet accepting calls and offering to take a message.
8. WHEN the Doctor updates any clinic configuration value, THE System SHALL apply the updated value to Voice_Front_Desk responses that begin within 5 seconds after the save completes, without requiring a restart.

### Requirement 2: Patient Appointment Booking by Voice

**User Story:** As a Patient, I want to book an appointment by voice, so that I can schedule a visit without waiting for a human receptionist.

#### Acceptance Criteria

1. WHEN a Patient requests to book an appointment AND names a service that matches a service offered in the Clinic_Knowledge_Base, THE Voice_Front_Desk SHALL set the requested service to the matched offered service.
2. WHEN a Patient requests to book an appointment for a matched offered service, THE Voice_Front_Desk SHALL invoke the check_availability Strands_Tool to retrieve open Slots for that service.
3. WHEN open Slots are available for the requested service, THE Voice_Front_Desk SHALL offer up to 3 available Slots to the Patient AND state the date and time of each offered Slot.
4. WHEN the Patient selects an offered Slot, THE Voice_Front_Desk SHALL state the selected Slot's date, time, service, and Provider and request the Patient's confirmation before booking.
5. WHEN the Patient confirms a selected Slot, THE Voice_Front_Desk SHALL invoke the book_appointment Strands_Tool to write the Appointment to the Provider's calendar through the AppointmentStore.
6. WHEN an Appointment is successfully booked, THE Voice_Front_Desk SHALL state the confirmed date, time, service, and Provider to the Patient.
7. IF no open Slots are available for the requested service, THEN THE Voice_Front_Desk SHALL offer to add the Patient to the Waitlist.
8. IF the book_appointment Strands_Tool fails to persist the Appointment, THEN THE Voice_Front_Desk SHALL inform the Patient that the booking did not complete, retain no partial Appointment, and offer to take a message.
9. IF a Patient requests to book an appointment AND names no service that matches a service offered in the Clinic_Knowledge_Base, THEN THE Voice_Front_Desk SHALL inform the Patient that the named service is not offered and ask the Patient to name an offered service.
10. IF the check_availability Strands_Tool fails to return Slots for the requested service, THEN THE Voice_Front_Desk SHALL inform the Patient that availability could not be retrieved and offer to take a message.

### Requirement 3: Patient Lookup and History

**User Story:** As a Patient, I want the Voice_Front_Desk to recognize me across calls, so that I do not have to repeat my information every time.

#### Acceptance Criteria

1. WHEN a Patient states their name and callback phone number during a Call_Session, THE Voice_Front_Desk SHALL invoke the lookup_patient Strands_Tool to retrieve any Patient record matching the provided name and callback phone number through the PatientStore.
2. IF exactly one matching Patient record is found, THEN THE Voice_Front_Desk SHALL use the retrieved Patient_History to inform the current Call_Session.
3. IF no matching Patient record is found, THEN THE Voice_Front_Desk SHALL collect the Patient's name and callback phone number required to create a new Patient record.
4. WHEN a new Patient provides the required name and callback phone number, THE Voice_Front_Desk SHALL create a Patient record through the PatientStore.
5. THE Voice_Front_Desk SHALL associate each booked Appointment with the corresponding Patient record.
6. IF more than one matching Patient record is found, THEN THE Voice_Front_Desk SHALL request additional identifying information from the Patient until exactly one Patient record matches or no Patient record matches.
7. IF the lookup_patient Strands_Tool fails to complete the retrieval, THEN THE Voice_Front_Desk SHALL inform the Patient that its records could not be accessed and offer to take a message.
8. IF the PatientStore fails to persist a new Patient record, THEN THE Voice_Front_Desk SHALL inform the Patient that the record could not be saved and offer to take a message.

### Requirement 4: Patient Appointment Rescheduling by Voice

**User Story:** As a Patient, I want to reschedule an existing appointment by voice, so that I can move my visit when my plans change.

#### Acceptance Criteria

1. WHEN a Patient requests to reschedule an Appointment, THE Voice_Front_Desk SHALL invoke the lookup_patient Strands_Tool to locate the Patient and the existing Appointment.
2. IF no existing Appointment is found for the Patient, THEN THE Voice_Front_Desk SHALL inform the Patient that no matching Appointment exists and offer to book a new Appointment.
3. IF more than one existing Appointment is found for the Patient, THEN THE Voice_Front_Desk SHALL ask the Patient to select which Appointment to reschedule until exactly one Appointment is selected.
4. WHEN exactly one existing Appointment is located or selected, THE Voice_Front_Desk SHALL invoke the check_availability Strands_Tool to retrieve alternative open Slots for the same service as the located Appointment.
5. IF no alternative open Slots are available for the located Appointment's service, THEN THE Voice_Front_Desk SHALL inform the Patient that no alternative Slots are available, leave the existing Appointment unchanged, and offer to add the Patient to the Waitlist.
6. WHEN the Patient selects an alternative Slot, THE Voice_Front_Desk SHALL state the new Slot's date, time, and service and request the Patient's confirmation before rescheduling.
7. WHEN the Patient confirms the new Slot, THE Voice_Front_Desk SHALL invoke the reschedule Strands_Tool to move the Appointment through the AppointmentStore.
8. WHEN an Appointment is successfully rescheduled, THE Voice_Front_Desk SHALL state the updated date, time, and service to the Patient and mark the previously held Slot as open.
9. IF the reschedule Strands_Tool fails to persist the change, THEN THE Voice_Front_Desk SHALL inform the Patient that the Appointment was not changed, leave the original Appointment unchanged, and offer to take a message.

### Requirement 5: Patient Appointment Cancellation by Voice

**User Story:** As a Patient, I want to cancel an appointment by voice, so that I can free the slot when I no longer need the visit.

#### Acceptance Criteria

1. WHEN a Patient requests to cancel an Appointment, THE Voice_Front_Desk SHALL invoke the lookup_patient Strands_Tool to locate the Patient through the PatientStore and the existing Appointment through the AppointmentStore.
2. IF no existing Appointment is found for the Patient, THEN THE Voice_Front_Desk SHALL inform the Patient that no matching Appointment exists.
3. IF more than one existing Appointment is found for the Patient, THEN THE Voice_Front_Desk SHALL ask the Patient to select which Appointment to cancel until exactly one Appointment is selected.
4. WHEN exactly one existing Appointment is located or selected, THE Voice_Front_Desk SHALL state the Appointment's date, time, service, and Provider and request the Patient's confirmation before cancelling.
5. WHEN the Patient confirms the cancellation, THE Voice_Front_Desk SHALL invoke the cancel Strands_Tool to remove the Appointment through the AppointmentStore.
6. IF the Patient declines to confirm the cancellation, THEN THE Voice_Front_Desk SHALL retain the Appointment and take no cancellation action.
7. WHEN an Appointment is successfully cancelled, THE Voice_Front_Desk SHALL confirm the cancellation to the Patient and mark the released Slot as open through the AppointmentStore.
8. IF the cancel Strands_Tool fails to persist the change, THEN THE Voice_Front_Desk SHALL inform the Patient that the Appointment was not cancelled, retain the Appointment unchanged, and offer to take a message.

### Requirement 6: Frequently Asked Questions

**User Story:** As a Patient, I want to ask common questions about the clinic by voice, so that I can get clinic information without waiting for a human.

#### Acceptance Criteria

1. WHEN a Patient asks a question about clinic hours, location, what to bring, preparation or fasting instructions, accepted insurance, or pricing for a named service, THE Voice_Front_Desk SHALL invoke the answer_faq Strands_Tool to retrieve the answer from the Clinic_Knowledge_Base.
2. WHEN the answer_faq Strands_Tool returns a single matching answer, THE Voice_Front_Desk SHALL state that answer to the Patient.
3. IF the answer_faq Strands_Tool returns no matching answer because the requested information is not present in the Clinic_Knowledge_Base, THEN THE Voice_Front_Desk SHALL inform the Patient that the information is unavailable and offer to take a message.
4. WHEN a Patient asks for pricing of a named service that is offered by the clinic AND has a configured price in the Clinic_Knowledge_Base, THE Voice_Front_Desk SHALL state the configured price for that service.
5. IF a Patient asks for pricing of a service that is not offered by the clinic OR that has no configured price in the Clinic_Knowledge_Base, THEN THE Voice_Front_Desk SHALL inform the Patient that the price is unavailable and offer to take a message.
6. IF the answer_faq Strands_Tool fails to return a result or returns an error, THEN THE Voice_Front_Desk SHALL inform the Patient that the requested information cannot be retrieved at this time and offer to take a message.
7. IF a Patient's question matches more than one FAQ topic, THEN THE Voice_Front_Desk SHALL ask the Patient to specify which information they need before invoking the answer_faq Strands_Tool.

### Requirement 7: Waitlist Management

**User Story:** As a Patient, I want to be added to a waitlist when my preferred slot is full, so that I can be offered the slot if it becomes available.

#### Acceptance Criteria

1. WHEN a Patient accepts an offer to join the Waitlist, THE Voice_Front_Desk SHALL invoke the add_to_waitlist Strands_Tool to record the Patient identifier, the requested service, the preferred Slot type, and the time the Patient was added through the Data_Layer.
2. WHEN a Patient is added to the Waitlist, THE Voice_Front_Desk SHALL confirm to the Patient the requested service and preferred Slot type recorded for the Waitlist placement.
3. THE System SHALL maintain the Waitlist for each requested service ordered by ascending time added, preserving the original insertion order for entries recorded at the same time.
4. IF the add_to_waitlist Strands_Tool fails to persist the entry, THEN THE Voice_Front_Desk SHALL inform the Patient that the Waitlist placement did not complete, retain no partial Waitlist entry, and offer to take a message.
5. IF a Patient accepts an offer to join the Waitlist for a requested service and preferred Slot type for which that Patient already has an active Waitlist entry, THEN THE Voice_Front_Desk SHALL inform the Patient that they are already on the Waitlist for that service and SHALL NOT create a duplicate entry.
6. IF a Patient declines the offer to join the Waitlist, THEN THE Voice_Front_Desk SHALL create no Waitlist entry and offer to take a message.

### Requirement 8: Gap Filling from Waitlist

**User Story:** As the Doctor, I want the System to offer to fill schedule gaps from the waitlist, so that open slots created by cancellations are recovered.

#### Acceptance Criteria

1. WHEN a Slot becomes open AND the Waitlist contains at least one Patient whose requested service equals the Slot's service, THE Practice_Intelligence SHALL generate a Decision recommending that the matching waitlisted Patients be contacted to fill the Slot.
2. WHEN the Doctor approves a gap-filling Decision, THE System SHALL invoke the fill_gap_from_waitlist Strands_Tool to select the matching Patient holding the earliest Waitlist position for the Slot's service.
3. WHEN a waitlisted Patient is selected to fill a gap, THE System SHALL associate the selected Patient with the open Slot as an Appointment through the AppointmentStore.
4. WHEN a waitlisted Patient is successfully assigned to fill a gap, THE System SHALL remove that Patient's matching Waitlist entry through the Data_Layer.
5. IF the fill_gap_from_waitlist Strands_Tool fails to persist the fill action, THEN THE System SHALL leave the Slot open, retain the Patient's Waitlist entry unchanged, and record that the gap fill did not complete through the Data_Layer.
6. IF no waitlisted Patient's requested service equals an open Slot's service, THEN THE System SHALL leave the Slot open and record no fill action.

### Requirement 9: Escalation to a Human

**User Story:** As a Patient, I want my request routed to a human when it is outside the agent's rules, so that unusual, clinical, or sensitive matters are handled appropriately.

#### Acceptance Criteria

1. IF a Patient asks a clinical question, requests a diagnosis, or requests symptom advice, THEN THE Voice_Front_Desk SHALL decline to answer the clinical content and invoke the flag_for_human Strands_Tool to escalate the request.
2. IF a Patient makes a request outside the Voice_Front_Desk's administrative rules, THEN THE Voice_Front_Desk SHALL invoke the flag_for_human Strands_Tool to escalate the request.
3. WHEN a Patient explicitly states anger, dissatisfaction, or distress, THE Voice_Front_Desk SHALL offer to escalate the request to a human.
4. WHEN a request is escalated, THE Voice_Front_Desk SHALL record the escalation reason as one of the categories clinical content, outside administrative rules, Patient distress, or Patient request, together with the Patient identity when known, and the Call_Session context through the Data_Layer.
5. WHEN a request is escalated, THE Voice_Front_Desk SHALL inform the Patient that a human will follow up and offer to take a message.
6. WHEN an Escalation is recorded, THE System SHALL surface the Escalation in the Dashboard call activity log within 5 seconds.
7. WHEN a Patient explicitly asks to speak with a human, THE Voice_Front_Desk SHALL invoke the flag_for_human Strands_Tool to escalate the request.
8. WHEN a Patient accepts an offer to escalate to a human, THE Voice_Front_Desk SHALL invoke the flag_for_human Strands_Tool to escalate the request.
9. IF the flag_for_human Strands_Tool fails to complete the escalation, THEN THE Voice_Front_Desk SHALL inform the Patient that the escalation could not be completed, retain the Call_Session context, and offer to take a message.

### Requirement 10: Administrative-Only Safety Guardrails

**User Story:** As the Doctor, I want the agent to stay strictly administrative, so that no clinical advice, triage, or diagnosis is ever given to Patients.

#### Acceptance Criteria

1. THE Voice_Front_Desk SHALL restrict its spoken responses to administrative and operational matters, defined as appointment booking, rescheduling, cancellation, waitlisting, clinic FAQs, and escalation, AND SHALL NOT provide clinical advice, symptom triage, diagnosis, treatment recommendations, or medication guidance.
2. WHEN a Patient names a symptom, THE Voice_Front_Desk SHALL route the request based only on the department, specialty, or service the Patient explicitly names.
3. WHEN a Patient names a symptom, THE Voice_Front_Desk SHALL NOT interpret the named symptom to infer or select a department, specialty, or service.
4. IF routing a request would require interpreting a Patient's symptom to select a department, specialty, or service, THEN THE Voice_Front_Desk SHALL NOT select a service, AND SHALL offer the clinic's configured general consultation if one is configured, AND SHALL invoke the flag_for_human Strands_Tool if none is configured.

   *Amended after a live call. A caller described nasal itching and asked which service to book; the agent declined and offered a human, and the call ended in a handover with 22 slots open that day. Every word of it followed 10.3, and it was still the wrong outcome.*

   *Offering the general consultation is not interpreting the symptom: it is the same answer for every symptom, so it conveys no clinical information, and a consultation is by definition the appointment at which the clinician decides what is needed. Selecting a specific investigation from a described symptom remains forbidden under 10.3 and always will be — the wrong test delays a real diagnosis. The service is offered, never selected: the Patient must accept it, at which point they have named it and 10.2 is satisfied unchanged.*

   *The offer is subordinate to every escalation path. A Patient who asks for a human, accepts an escalation offer, expresses distress, asks a clinical question, or reports an emergency still reaches a human; only a Patient who is calmly unsure is offered the consultation.*
5. WHEN a Patient requests a clinical decision or a clinic-policy decision, THE Voice_Front_Desk SHALL decline to make the decision AND invoke the flag_for_human Strands_Tool to defer the decision to a human.
6. WHEN a Patient requests clinical advice, a diagnosis, or symptom triage, THE Voice_Front_Desk SHALL decline to provide the clinical content AND state that clinical questions are handled by clinic staff.

### Requirement 11: Conversational Context and Multi-Step Reasoning

**User Story:** As a Patient, I want the agent to remember what I said earlier in the call and complete multi-step tasks, so that the conversation feels natural and efficient.

#### Acceptance Criteria

1. WHILE a Call_Session is active, THE Voice_Front_Desk SHALL retain the Patient's provided identifying details, requested service, requested date, requested time, and Slot selection for the duration of that Call_Session.
2. WHEN a task requires multiple Strands_Tool invocations, THE Voice_Front_Desk SHALL chain the required Strands_Tools in sequence such that each completed Strands_Tool's output informs the next Strands_Tool invocation until the task completes.
3. IF a Strands_Tool invocation fails partway through a chained task, THEN THE Voice_Front_Desk SHALL retain the context gathered so far, inform the Patient that the request could not be completed, and offer to take a message.
4. WHEN a Patient references information provided earlier in the same Call_Session, THE Voice_Front_Desk SHALL use that information without asking the Patient to repeat it.
5. WHEN a Call_Session ends, THE System SHALL persist the Call_Session outcome as one of booked, rescheduled, cancelled, waitlisted, escalated, or no action, together with the Patient-provided identifying information, to the Data_Layer for use in future Call_Sessions.

### Requirement 12: Real-Time Voice Interaction and Interruption Handling

**User Story:** As a Patient, I want the voice conversation to feel natural and responsive, so that talking to the agent is as easy as talking to a person.

#### Acceptance Criteria

1. WHEN a Patient finishes speaking, THE Voice_Front_Desk SHALL begin an audible spoken response within 1.5 seconds.
2. WHILE the Voice_Front_Desk is speaking AND a Barge_In is detected, THE Voice_Front_Desk SHALL stop speaking within 500 milliseconds and process the Patient's new speech.
3. WHEN a Barge_In interrupts a spoken response, THE Voice_Front_Desk SHALL retain the current task context and resume the task from its pre-interruption step after processing the interruption.
4. IF the Voice_Front_Desk cannot interpret the Patient's speech, THEN THE Voice_Front_Desk SHALL ask the Patient to repeat or rephrase the request, up to a maximum of 2 consecutive interpretation-failure attempts for the same request.
5. IF the Voice_Front_Desk reaches the maximum of 2 consecutive interpretation-failure attempts for the same request, THEN THE Voice_Front_Desk SHALL invoke the flag_for_human Strands_Tool and inform the Patient that a human will follow up.
6. IF a Patient provides no speech for 10 seconds during a Call_Session, THEN THE Voice_Front_Desk SHALL re-prompt the Patient once.
7. IF the voice layer becomes unavailable during a Call_Session, THEN THE System SHALL inform the Patient that the call cannot continue, end the Call_Session, and record the Call_Session as interrupted through the Data_Layer.

### Requirement 13: Autonomous Practice Intelligence Analysis

**User Story:** As the Doctor, I want the System to analyze operational patterns in the background, so that I can act on real problems without reviewing raw data myself.

#### Acceptance Criteria

1. THE Practice_Intelligence SHALL start an analysis run on a recurring interval not exceeding 24 hours.
2. WHEN an analysis run starts, THE Practice_Intelligence SHALL invoke the analyze_patterns Strands_Tool over Appointment, Waitlist, and Call_Session data.
3. WHEN the analyze_patterns Strands_Tool detects a no-show trend, a schedule utilization or gap pattern, unmet demand, or repeated requests for an unoffered service AND no open Decision for the same finding already exists, THE Practice_Intelligence SHALL generate a Decision describing the finding and a recommended action.
4. THE Practice_Intelligence SHALL generate a Decision only when the finding maps to an action the Doctor can approve or dismiss.
5. WHEN Practice_Intelligence generates a Decision, THE System SHALL persist the Decision through the Data_Layer.
6. IF fewer than 5 relevant records exist to support a finding, THEN THE Practice_Intelligence SHALL generate no Decision for that finding.
7. IF the analyze_patterns Strands_Tool fails during an analysis run, THEN THE Practice_Intelligence SHALL generate no Decision and record the analysis failure through the Data_Layer.
8. IF persistence of a generated Decision fails, THEN THE System SHALL retain the finding for a later analysis run AND SHALL NOT create a duplicate Decision.

### Requirement 14: Doctor Dashboard - Decisions Feed

**User Story:** As the Doctor, I want a feed of decisions to make with approve and dismiss controls, so that I can act on the System's recommendations quickly.

#### Acceptance Criteria

1. THE Dashboard SHALL display a "Decisions to make" feed listing each open Decision generated by Practice_Intelligence, ordered from most recently generated to least recently generated.
2. THE Dashboard SHALL display an approve control and a dismiss control for each open Decision listed in the feed.
3. WHEN the Doctor approves a Decision, THE System SHALL record the approval through the Data_Layer AND execute the Decision's associated action through the Data_Layer.
4. WHEN the Doctor dismisses a Decision, THE System SHALL record the dismissal through the Data_Layer.
5. WHEN a Decision's approval and its associated action complete successfully, OR WHEN a Decision is dismissed, THE System SHALL remove the Decision from the open Decisions feed within 2 seconds.
6. IF executing an approved Decision's associated action fails to persist through the Data_Layer, THEN THE System SHALL retain the Decision in the open Decisions feed as open AND display an error indication that the action did not complete.
7. WHILE no open Decision exists, THE Dashboard SHALL display an empty-state message in the "Decisions to make" feed indicating there are no decisions to review.
8. WHEN Practice_Intelligence persists a new Decision through the Data_Layer, THE Dashboard SHALL add the Decision to the open Decisions feed within 5 seconds.

### Requirement 15: Doctor Dashboard - Schedule, Activity, and Metrics

**User Story:** As the Doctor, I want to see today's schedule, call activity, and impact metrics, so that I can understand what the agent is doing and its value.

#### Acceptance Criteria

1. WHEN the Doctor opens the schedule view, THE Dashboard SHALL display the Provider's Appointments and open Slots for the current day by default.
2. THE Dashboard SHALL display a call activity log in which each entry shows the interaction type (booked, rescheduled, cancelled, or escalated), the date and time of the interaction, and the associated Patient identifier, ordered from most recent to oldest.
3. THE Dashboard SHALL display an impact metrics strip showing front-desk hours saved, the count of Appointments recovered from the Waitlist, and the no-show rate, each computed over a Doctor-selectable reporting period of 7, 30, or 90 days, with the no-show rate trend shown as the change in no-show rate relative to the immediately preceding period of equal length.
4. WHEN an Appointment is booked, rescheduled, or cancelled through the Voice_Front_Desk, THE Dashboard SHALL reflect the change in the schedule view and the call activity log within 5 seconds.
5. WHERE a viewer is assigned a role, THE Dashboard SHALL present only the schedule view, call activity log, and impact metrics strip permitted for that assigned role.
6. WHEN the Doctor selects a day other than the current day in the schedule view, THE Dashboard SHALL display the selected day's Appointments and open Slots within 2 seconds.
7. IF a viewer without an assigned role attempts to access the Dashboard, THEN THE Dashboard SHALL deny access and present no schedule, call activity, or metrics data.

### Requirement 16: Data Layer and Provider-Aware Model

**User Story:** As the Doctor, I want clinic data stored behind a clean, swappable interface, so that the System is maintainable and can grow beyond a single provider.

#### Acceptance Criteria

1. THE Data_Layer SHALL expose a distinct data-access interface, including AppointmentStore and PatientStore, for each persisted record type (Appointment, Patient, Waitlist, Decision, Clinic_Knowledge_Base, and Call_Session), such that the Voice_Front_Desk and Practice_Intelligence read and write records only through these interfaces and never access the underlying storage directly.
2. WHEN the Voice_Front_Desk or Practice_Intelligence writes an Appointment, Patient, Waitlist, Decision, Clinic_Knowledge_Base, or Call_Session record, THE Data_Layer SHALL persist the record to DynamoDB and return a success result to the caller.
3. THE Data_Layer SHALL associate each Appointment, Slot, and schedule record with exactly one Provider identifier.
4. WHEN the System is first initialized, THE Data_Layer SHALL contain no pre-seeded Appointment or Patient records AND SHALL return an empty result set for read operations against the AppointmentStore and PatientStore until records are written.
5. WHERE the underlying storage backing the Data_Layer is replaced, THE Data_Layer SHALL expose the same data-access interfaces and operation signatures such that read and write operations invoked by the Voice_Front_Desk and Practice_Intelligence produce equivalent observable results without modification to Voice_Front_Desk or Practice_Intelligence code.
6. IF a write operation through any Data_Layer interface fails to persist, THEN THE Data_Layer SHALL return a failure result indicating the write did not complete AND SHALL leave previously stored records unchanged.
7. IF a write of an Appointment, Slot, or schedule record is attempted without a Provider identifier, THEN THE Data_Layer SHALL reject the write and return a failure result indicating the missing Provider identifier.
